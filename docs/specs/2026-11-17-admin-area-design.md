# Раздел «Администрирование» в веб-интерфейсе

## Зачем

Админ (логин из `server.auth.admins`) видит все пространства, но только по
одному, через переключатель в шапке. Пространства, их участники и ключи API
меняются только командами `spacesCli` и `apiKeysCli` на сервере, под root.
Нужен раздел, где админ:

1. видит все рассылки всех пространств одной таблицей;
2. управляет пространствами: создаёт, меняет название и From, удаляет пустые,
   добавляет и убирает участников, переносит рассылки между пространствами;
3. управляет ключами API: видит список, выпускает ключ (значение показывается
   один раз), меняет роль, отзывает.

Тем же API должен уметь пользоваться ключ Claude: скрипты рассылок сами заводят
пространства и ключи.

Готово, когда: человек из `server.auth.admins` открывает «Администрирование»,
видит рассылки всех пространств, создаёт пространство с участником и выпускает
ключ этого пространства; ключ с ролью `--admin` может сделать то же через API;
ключи system, space и proxy без логина админа получают 403 на `/admin/*`.

## Кто админ

- запрос с ключом прокси, если `X-Remote-User` есть в `server.auth.admins`;
- ключ с новой ролью `admin` (`apiKeysCli add|set-role <имя> --admin`). Как и
  system, он видит все пространства и вдобавок получает `/admin/*`.

Ключи system, legacy и запросы без ключа админского доступа не получают, даже
когда `server.auth.required: false`. Список админов-людей задаётся только в
конфиге: из интерфейса его не поменять, чтобы админ не лишил себя прав.

## API

Все маршруты `/admin/*` проходят проверку `requireAdmin`: если запрос не от
админа, ответ 403 `ADMIN_REQUIRED`.

- `GET /me` — `{ key?, user?, admin }`, доступен любому ключу. По нему клиент
  решает, показывать ли ссылку на админку.
- Все рассылки: `GET /mailings` без `X-Eterpost-Space`. Админ видит все
  пространства, у каждой рассылки есть поле `space`. Нового маршрута не нужно.
- `POST /admin/mailings/:id/move` `{space}`: перенести рассылку в другое
  пространство. Пространства нет — 404 `SPACE_NOT_FOUND`.
- `GET /admin/spaces`: все пространства (`default` есть всегда) с участниками и
  числом рассылок.
- `POST /admin/spaces` `{name, title?, from?}`: создать. Имя проверяется по
  шаблону, если такое уже есть — 409 `SPACE_EXISTS`.
- `PUT /admin/spaces/:name` `{title?, from?}`: изменить.
- `DELETE /admin/spaces/:name`: удалить. Если в пространстве есть рассылки —
  409 `SPACE_NOT_EMPTY`. `default` удалить нельзя (400).
- `PUT /admin/spaces/:name/members/:login`, `DELETE ...`: добавить или убрать
  участника. Логин — непустая строка без пробелов, до 64 символов.
- `GET /admin/keys`: имя, роль, когда создан, когда последний раз
  использовался. Хеш не отдаётся, отмечен ключ текущего запроса (`current`).
- `POST /admin/keys` `{name, role}`: выпустить ключ. Значение приходит
  только в этом ответе (`{name, key}`) и в журнал не пишется. Если имя занято —
  409 `KEY_EXISTS`.
- `PUT /admin/keys/:name/role` `{role}`: сменить роль.
- `DELETE /admin/keys/:name`: отозвать. Ключи прокси отзываются только с
  `?force=1`, без него — 409 `PROXY_KEY`: через них работает вход в веб-интерфейс.

Роль в API: `{ type: 'space', space } | { type: 'system' } | { type: 'admin' }
| { type: 'proxy' }`. Legacy через API назначить нельзя, такие ключи только
показываются в списке.

Защита от потери доступа: нельзя отозвать ключ, через который сделан запрос, и
нельзя сменить его роль (409 `OWN_KEY`).

Журнал: все изменяющие запросы и сейчас пишутся с ключом, пользователем и
списком полей тела. Для ключей дополнительно пишется
`admin: key "x" issued (role) by …`, `... revoked`, `... role changed`, а для
пространств — `space "x" created/updated/removed`, `member added/removed`,
`mailing #N moved a → b`.

## Экраны

Вход: если `GET /me` вернул `admin: true`, под шапкой появляется ссылка
«Администрирование» (`?view=admin&tab=mailings|spaces|keys`). Ссылка
«← К рассылкам» возвращает обычный вид. Состояние хранится в адресе.

**Все рассылки.** Таблица: пространство, название с пометкой «проба»,
состояние, отправлено и ошибки. Фильтры: пространство, состояние,
боевые/пробные/все, поиск по названию. Сверху сводка, сколько рассылок идёт
сейчас и в каких пространствах. Клик по строке открывает рассылку в её
пространстве в обычном виде. В строке есть действие «Перенести в…».

**Пространства.** Карточка на каждое пространство: имя, название и From
редактируются на месте, число рассылок (ссылка на вкладку «Все рассылки» с
фильтром), участники чипами с удалением и поле «добавить логин». Кнопка
«Удалить» доступна только для пустого пространства. Над списком — форма
«Новое пространство».

**Ключи API.** Таблица: имя, роль, создан, последнее использование. Выпуск
ключа: имя и роль, затем окно с ключом, кнопкой «Скопировать» и
предупреждением, что ключ показан один раз. Смена роли и отзыв — с
подтверждением, для ключей прокси предупреждение отдельное. Для своего ключа
действия недоступны. Legacy-ключи помечены.

Ошибки и успехи показываются существующими уведомлениями. После каждого
изменения список перечитывается.

## Тесты и выкатка

- Сервер (node:test, Redis): роль admin в репозитории и CLI; `requireAdmin` —
  доступ для админа через прокси и для ключа admin, 403 для system, space,
  proxy без логина админа и legacy; все маршруты `/admin/*`, включая
  ошибки (занятое имя, непустое пространство, свой ключ, ключ прокси без force);
  выпущенный ключ сразу работает.
- Клиент: `typecheck`, `lint`, сборка; проверка в браузере на стенде.
- Стенд e2e: админ создаёт пространство, выпускает ключ пространства и этим
  ключом создаёт рассылку.
- Выкатка: релиз 0.5.0, затем `update.sh`. После этого ключу `claude` даётся
  роль `admin` (`apiKeysCli set-role claude --admin`).
