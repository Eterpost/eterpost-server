# Вложения в рассылках

Задача: https://bugs.etersoft.ru/show_bug.cgi?id=20027

## Зачем

Нужно рассылать файлы, прежде всего прайс-листы в PDF, как настоящие вложения
письма. Сейчас в mail-server есть только неиспользуемое поле `Email.attachments`
(2018): его никто не заполняет, файлы негде хранить, в API и веб-интерфейсе
вложений нет.

Готово, когда: к рассылке через веб-интерфейс или API прикладывается PDF;
пробное письмо и письма рассылки приходят с этим PDF во вложении, и он
открывается; дубль рассылки и повтор по ошибкам доставки уходят с теми же
вложениями; при удалении рассылки её файлы удаляются.

Не входит: картинки в тексте письма по URL (ipfs-images, абсолютные адреса в
редакторе) — отдельная задача.

## Хранение

Файлы лежат на диске в каталоге `server.attachments.dir`, в Redis их нет.

```
<dir>/<номер рассылки>/<id вложения>
```

`id` — 16 случайных шестнадцатеричных символов; имя файла пользователя в путь
не попадает, поэтому обход каталогов через имя невозможен.

Описания вложений хранятся в свойствах рассылки (JSON в Redis, рядом с `html`,
`subject`):

```json
"attachments": [
  { "id": "9f2c…", "filename": "Прайс ноябрь.pdf",
    "contentType": "application/pdf", "size": 834512 }
]
```

Порядок в массиве — порядок вложений в письме. mail-sorter переписывает JSON
рассылки целиком (`updateJsonInTransaction`) и неизвестные поля сохраняет —
его менять не нужно.

Каталог по умолчанию:

- в `config.default.json` — `data/attachments` (относительно рабочего каталога:
  для разработки и стенда);
- в `deploy/lxc/config/mail-server.json` — `/var/lib/eterfund-mail/attachments`;
  в юните `mail-server.service` добавляется `StateDirectory=eterfund-mail`:
  systemd создаёт `/var/lib/eterfund-mail` с владельцем `mailing`, и он
  доступен на запись при `ProtectSystem=strict`.

При запуске сервер создаёт каталог (`mkdir -p`). Если это не удалось, сервер
пишет ошибку в журнал и работает дальше, а маршруты вложений отвечают 503 —
рассылки без вложений не должны ломаться из-за каталога.

Бэкап: каталог входит в снимок контейнера; отдельного бэкапа нет. Вложения без
описания в рассылке (недописанная загрузка, сбой при удалении) безвредны и не
отправляются.

## Ограничения

- `server.attachments.maxSize` — общий размер вложений рассылки, по умолчанию
  10 МБ (10485760). base64 увеличивает письмо примерно на треть: около 14 МБ,
  что проходит через большинство почтовых серверов (лимит обычно 20–25 МБ).
  Загрузка сверх лимита — 413.
- Тип файла — любой. `contentType` — из заголовка Content-Type загрузки, если он
  не пустой и не `application/octet-stream`; иначе по расширению
  (`detectMimeType` из `nodemailer/lib/mime-funcs/mime-types`, неизвестное
  расширение — `application/octet-stream`).
- Имя файла: берётся последняя часть пути, убираются управляющие символы,
  обрезается до 200 символов; пустое имя — 400.
- Менять вложения выполняющейся рассылки (RUNNING) нельзя — 409: письма одной
  рассылки должны быть одинаковыми.

## API

Все маршруты с номером рассылки идут через `loadMailing`: рассылка чужого
пространства — 404.

| Запрос | Что делает |
|--------|------------|
| `POST /mailings/:id/attachments?filename=<имя>` | Тело — сам файл (любой Content-Type). Ответ — описание вложения |
| `GET /mailings/:id/attachments/:attachmentId` | Скачать файл (`Content-Disposition: attachment` с именем) |
| `DELETE /mailings/:id/attachments/:attachmentId` | Удалить вложение |
| `GET /mailings/:id` | Как и сейчас, в рассылке есть `attachments` |
| `POST /mailings` | Новое поле `attachments: [{filename, contentType?, content}]`, `content` — base64: скрипт создаёт рассылку с прайсом одним запросом. С `sourceId` (дублирование) вложения копируются из исходной рассылки |
| `POST /mailings/create-retry` | Вложения копируются из исходной рассылки |
| `DELETE /mailings/:id` | Удаляет и каталог вложений рассылки |
| `PUT /mailings/:id` | Поле `attachments` в теле игнорируется: вложения меняются только своими маршрутами |

Сейчас `createExpressServer` разбирает тело любого POST как JSON. Маршрут
загрузки должен получать тело как есть: общий парсер пропускает
`/mailings/:id/attachments`, а маршрут использует
`express.raw({ type: () => true, limit: maxSize })`.

Ошибки — в обычном формате `error(...)`. Коды: 400 (нет имени), 404 (нет
рассылки или вложения), 409 (рассылка выполняется), 413 (превышен размер),
503 (каталог недоступен).

OpenAPI (`server/src/openapi.ts`) описывает новые маршруты и поля.

## Компоненты

- `AttachmentStore` (`server/src/AttachmentStore.ts`) — файлы на диске:
  `save(mailingId, content) → id` (запись во временный файл и rename),
  `path(mailingId, id)`, `copy(fromMailingId, toMailingId, attachments) →
  attachments с новыми id`, `remove(mailingId, id)`, `removeAll(mailingId)`,
  `exists(mailingId, id)`. Ничего не знает о Redis и HTTP.
- `attachments.ts` (`server/src/attachments.ts`) — чистые функции: описание
  вложения, нормализация имени, определение типа, проверка лимита.
- `MailingProperties.attachments` / `Mailing.attachments` — описания; репозиторий
  сохраняет поле в `create` и при сериализации.
- Контроллеры `controllers/attachments.ts`: загрузка, скачивание, удаление.
  Описание добавляется и удаляется через `updateInTransaction`, чтобы не
  затереть параллельные изменения рассылки (mail-sorter, отправка).
  Порядок: загрузка — файл, затем описание (при ошибке файл удаляется);
  удаление — описание, затем файл.
- `addMailing`, `createRetryMailing`, `deleteMailing` — копирование и удаление.

## Отправка

`MailingExecutor.createEmail` добавляет в `Email` вложения рассылки в виде
`{ filename, contentType, path }`: nodemailer читает файл сам при сборке
каждого письма, в памяти файлы не держатся.

Перед запуском рассылки (`startExecution`) и перед пробным письмом сервер
проверяет, что все файлы на месте. Если файла нет, рассылка не запускается
(ошибка с именем пропавшего файла в журнале и в ответе API), а не уходит без
вложения.

`Email.Attachment` расширяется: `content` или `path`, плюс `contentType`.

Предпросмотр (`/mailings/:id/preview`, `/preview`) возвращает список вложений
(имя, тип, размер), без содержимого.

## Веб-интерфейс

На карточке рассылки — блок «Вложения» под редактором:

- список: имя (ссылка на скачивание), размер, кнопка удаления;
- кнопка «Добавить файл» (можно выбрать несколько) и подсказка «до 10 МБ на
  письмо»; значение лимита приходит с сервера вместе с рассылкой
  (`attachmentsMaxSize` в ответе `GET /mailings/:id`);
- пока рассылка выполняется, блок только для чтения;
- ошибки загрузки — обычными уведомлениями (`notifyAboutError`).

Дублирование рассылки идёт через `sourceId`, поэтому копирует вложения без
изменений в клиенте.

## Развёртывание

1. Юнит `mail-server.service` с `StateDirectory=eterfund-mail` — `update.sh`
   юниты не ставит: на проде юнит обновляется вручную (`install` +
   `systemctl daemon-reload`), до перезапуска с новым релизом.
2. В `/etc/eterfund-mail/mail-server.json` — `server.attachments.dir`
   (`/var/lib/eterfund-mail/attachments`); без него сервер возьмёт
   `data/attachments` в каталоге релиза, который read-only, и вложения будут
   недоступны (503).
3. nginx: `client_max_body_size 50m` на `/api/` уже есть.
4. README (ru/en), `deploy/lxc/README.md`, CHANGELOG.
