# Пространства рассылок и пробные рассылки

Задача: https://bugs.etersoft.ru/show_bug.cgi?id=20010

## Зачем

Сейчас все рассылки лежат в одном списке. Любой ключ API и любой, кто вошёл в
веб-интерфейс, видит, правит и может запустить чужую рассылку, а пробные
отправки одного отправителя (например, sales) смешиваются с рассылками других.

Цель:

- рассылки делятся по пространствам; список, просмотр, статистика и действия с
  рассылкой доступны только в её пространстве;
- пространство привязано к ключу API;
- в веб-интерфейсе человек работает в одном из своих пространств и может
  переключаться между ними;
- пробные рассылки помечены признаком и по умолчанию не показываются в списке,
  но их история сохраняется.

Готово, когда: ключ пространства sales не видит и не может открыть рассылку
пространства news (ответ 404); человек, который входит только в sales, в
веб-интерфейсе видит только рассылки sales; пробные рассылки скрыты фильтром
«боевые» и видны в «пробные» и «все».

## Понятия

**Пространство** — имя (`[a-z0-9][a-z0-9-]{0,31}`), название для людей,
адрес отправителя по умолчанию и список участников (логины, которые фронт
передаёт в `X-Remote-User`). Хранится в Redis.

**Ключ API** получает одну из ролей:

| Роль | Кому | Что видит |
|------|------|-----------|
| пространство (`--space sales`) | сайты и скрипты отправителя | только рассылки своего пространства |
| служебный (`--system`) | mail-sorter, subscription-facade | все рассылки; нужен для отписки, подписки, счётчиков и разбора возвратов |
| прокси (`--proxy`, уже есть) | фронт веб-интерфейса | пространства пользователя из `X-Remote-User` |

**Администраторы** — логины в `server.auth.admins` (конфиг). Через ключ прокси
они видят все пространства и могут переключаться между ними.

## Доступ к рассылкам

1. `apiKeyAuth` после проверки ключа определяет, к каким пространствам у запроса
   есть доступ, и кладёт это в `res.locals.actor`:
   - ключ пространства — к одному своему;
   - служебный ключ — ко всем;
   - ключ прокси — к пространствам, где пользователь в участниках, или ко всем,
     если он администратор. Без `X-Remote-User` — ни к одному, кроме случая,
     когда ни у одного пространства нет участников: тогда — к `default`
     (см. «Переход для работающей установки»). Изоляция действует, только когда
     включён `server.auth.required` и не осталось ключей без роли: запрос без
     ключа и старый ключ видят все пространства.
2. Текущее пространство запроса задаёт заголовок `X-Eterpost-Space` (его шлёт
   веб-интерфейс). У ключа пространства заголовок не нужен, у служебного
   необязателен (без него — все пространства). Заголовок с пространством, к
   которому нет доступа, — ответ 403.
3. Все маршруты `/mailings/:id/...` получают рассылку через одну общую
   промежуточную функцию: она загружает рассылку и проверяет её пространство.
   Рассылка чужого пространства — ответ 404, как будто её нет: так её номер
   нельзя подобрать. Контроллеры получают уже проверенную рассылку из
   `res.locals.mailing`, и забыть проверку в новом маршруте нельзя.
4. `GET /mailings` возвращает только рассылки текущего пространства — никакой
   запрос (кроме служебного ключа) не получает рассылки чужих пространств.
   `POST /mailings` и `POST /mailings/create-retry` записывают рассылку в
   текущее пространство; для повтора исходная рассылка должна быть в нём же.
5. Не зависят от пространства: `POST /preview` (рассылки нет),
   `GET /sorter/status`, описание API.

## Отписка от всех рассылок

Отписка письмом (кнопка List-Unsubscribe, `mailto:`) действует в пределах
пространства рассылки, из которой пришло письмо.

- В адрес отписки добавляется номер рассылки: `server.mail.listUnsubscribe`
  принимает подстановку `{id}`, например
  `<mailto:noreply+unsubscribe-{id}@example.com>`. Без `{id}` — как сейчас
  (адрес без номера).
- mail-sorter узнаёт адрес отписки по части после `+`: `unsubscribe` (старые
  письма) или `unsubscribe-<номер>`. С номером он передаёт его в
  `POST /mailings/unsubscribe` как `mailingId`.
- mail-server с `mailingId` исключает адрес из всех рассылок с `listUnsubscribe`
  в пространстве этой рассылки. Без номера (письма, отправленные до перехода)
  — из всех пространств, как сейчас.
- Исключение из-за ошибок доставки остаётся общим: несуществующий адрес не
  существует ни для кого.
- Отписка по ссылке (subscription-facade) и сейчас касается одной рассылки —
  без изменений.
- `POST /mailings/unsubscribe` доступен только служебному ключу.

## Адрес отправителя

From письма выбирается по порядку: адрес рассылки (`from`, если задан), адрес
пространства, `server.mail.from`. Sender и конверт — по-прежнему адрес сервиса
(`server.mail.from`): возвраты разбирает mail-sorter. В форме рассылки поле
From пустое, а подсказкой показан адрес пространства. Адрес пространства
задаётся в CLI (`spaces add … --from`, `spaces set … --from`).

## Пробные рассылки

- Новое поле рассылки `test: boolean` (по умолчанию `false`). Задаётся при
  создании и правке: в API и флажком «Пробная» в форме рассылки.
- `GET /mailings?kind=live|test|all` — фильтр внутри текущего пространства;
  по умолчанию в API — `all` (боевые и пробные своего пространства), чтобы
  старые клиенты не потеряли свои пробные рассылки. Веб-интерфейс по умолчанию показывает `live` и
  запоминает выбор в адресе страницы.
- В списке у пробной рассылки пометка «проба».
- Ошибки доставки пробных рассылок учитываются в статистике адресов так же, как
  у боевых: мёртвый адрес мёртв в любой рассылке.
- Тестовое письмо (`send-test-email`) — по-прежнему не рассылка, без изменений.

## Веб-интерфейс

- После загрузки клиент запрашивает `GET /spaces` — пространства, доступные
  пользователю (имя, название). Если пространство одно, переключателя нет; если
  несколько — выпадающий список в шапке. Если ни одного — сообщение «Вас ещё не
  добавили ни в одно пространство, обратитесь к администратору».
- Текущее пространство — в адресе страницы (`?space=sales`), чтобы ссылкой на
  рассылку можно было поделиться; без него — последнее выбранное (localStorage)
  или первое из списка.
- Каждый запрос к API несёт `X-Eterpost-Space`.

## Управление

Через CLI (как ключи API), веб-управление — позже, отдельной задачей:

```
spaces add <имя> [--title "Название"] [--from "Имя <адрес>"]
spaces set <имя> [--title …] [--from …]
spaces list
spaces members <имя>                  участники
spaces add-member <имя> <логин>
spaces remove-member <имя> <логин>
spaces remove <имя>                   только пустое пространство
spaces move <номер рассылки> <имя>    перенести рассылку в другое пространство
                                      (пространство и рассылка должны существовать;
                                      `default` допустимо)

api-keys add <имя> --space <пространство> | --system | --proxy
```

`api-keys list` показывает роль и пространство ключа.

## Переход для работающей установки

1. При первом запуске новой версии все рассылки без пространства попадают в
   пространство `default` (поле в JSON рассылки дописывается один раз, в журнал —
   сколько перенесено).
2. Старые ключи без роли продолжают работать как раньше — со всеми
   рассылками — и при каждом использовании пишут предупреждение в журнал, пока
   им не назначат роль: `api-keys set-role <имя> --space … | --system`.
3. Ключ прокси без настроенных участников: пока ни у одного пространства нет
   участников, пользователь прокси видит `default` (иначе после обновления
   веб-интерфейс опустеет) — в том числе запрос без `X-Remote-User`. Как только
   участники заведены, действует проверка: запрос без пользователя не видит
   ничего.
4. В README и deploy/lxc — порядок перехода: завести пространства и участников,
   назначить роли ключам mail-sorter и subscription-facade (`--system`), сайтам —
   пространства (сначала перенести рассылки сайта в это пространство командой
   `spaces move`, иначе сайт получит 404 на свои рассылки), обновить mail-sorter (он принимает оба вида адреса —
   `unsubscribe` и `unsubscribe-<номер>`), только затем добавить `{id}` в
   `server.mail.listUnsubscribe` (старый mail-sorter не распознаёт адрес с
   номером, и отписки из новых писем пропадают), затем убедиться по журналу,
   что предупреждений нет.

## Хранение (Redis)

- `SPACES` — hash: имя → JSON `{ title, from, createdAt }`.
- `SPACE_MEMBERS_<имя>` — set логинов.
- Рассылка: поле `space` в общем JSON рассылки. Список пространства —
  фильтрацией `getAll()`, как сейчас. Отдельный индекс не нужен: рассылок
  сотни, а не миллионы.
- Ключ API: поля `space?: string` и `system?: boolean` в записи ключа.

## Проверка

- Модульные тесты: роли ключей и доступ (`apiKeyAuth`), промежуточная функция
  рассылки (своя, чужая — 404, нет такой — 404), `GET /mailings` по
  пространству и `kind`, создание и повтор в текущем пространстве, перенос
  старых рассылок в `default`, совместимость старых ключей; выбор From
  (рассылка, пространство, сервер); `{id}` в List-Unsubscribe; отписка с
  `mailingId` только в своём пространстве и без него — во всех.
- mail-sorter: разбор `unsubscribe-<номер>` и `unsubscribe`, передача
  `mailingId`.
- `openapi.test` — новые маршруты и параметры описаны.
- Стенд (`stand/`): mail-sorter и subscription-facade со служебными ключами —
  сквозные тесты проходят.
- Веб-интерфейс вживую: переключение пространств, фильтр проб, сообщение для
  пользователя без пространств.

## Не входит

- Веб-управление пространствами и участниками.
- Свой SMTP-сервер на пространство — при необходимости отдельной задачей.
